# 重複設定安全網消融實驗:`final_results_30` vs `final_results_30_noretry`

> 本文比較的是**同一批 30-trial 實驗設計**在「安全網開(`final_results_30`)」與
> 「安全網關(`final_results_30_noretry`)」兩種條件下的差異,而不是單獨分析
> `final_results_30` 本身——`final_results_30` 的獨立結論(7 種方法的主要比較)跟
> `final_results/`(20-trial)是同一套故事、只是預算更大更明顯,已經在
> [`EXPERIMENT_OVERVIEW.md`](EXPERIMENT_OVERVIEW.md) §4.2 講完,沒有另外開文件的必要;
> 這裡處理的是它作為「有安全網對照組」時,獨有的、只有跟 noretry 放在一起看才有意義的內容。
>
> 內容整理自 `dashboard/pages_custom/report_30trial_noretry.py`(「No-Retry 消融 (30 Trial)」頁)
> 內建的分析報告,把原本只存在於該頁 Python 字串裡的結論萃取成獨立文件,方便引用與分享。
> 互動版本、原始圖表請見 `streamlit run dashboard/app.py`。數字口徑與該頁一致。

## 1. 背景與研究問題

`orchestrator.py` 有一個「去重複重試」安全網:LLM 若建議了已經試過的配置,系統不會把這次
建議正式記成一個 trial,而是**不重打 API、最多重試 5 次**去要一個新建議,這整個過程完全
不會出現在正式的 30 個 trial 記錄裡——換句話說,使用者平常看到的「30 個 trial」,其實可能
背地裡多燒了好幾次隱藏的 API 呼叫。

這批實驗把安全網關掉(`_MAX_DUP_RETRIES` 從 5 改成 1):LLM 建議重複配置時,直接把該
iteration 記成「重複 config,已跳過」的浪費 trial,不重打 API。目的是回答:

> **拿掉安全網之後,各記憶策略原始的「記憶可靠度」差多少?這個安全網,到底是在保護「最終結果」還是「trial 預算的使用效率」?**

TPE / NSGA-II / Random 這三個統計方法本來就不會建議完全相同的浮點數配置,這個消融實驗
對它們沒有意義,所以本篇所有跟統計方法有關的比較,都是直接沿用 `final_results_30`
(同樣 30-trial、有安全網)的資料作為基準。

## 2. 實驗設計

| 項目 | 設定 |
|---|---|
| 模型 / 任務 | Llama-3.2-3B-Instruct / GSM8K |
| Trial 預算 | 30 trial × 3 run |
| 涵蓋方法 | 僅 4 種 LLM 記憶策略(`full` / `window` / `summary` / `tool`) |
| 安全網 | **關**(`_MAX_DUP_RETRIES=1`,重複建議直接記為跳過) |
| 對照組 | `final_results_30`(同樣 30-trial,安全網**開**) |
| Token 記錄 | 這批資料是在 `llm_client.py` 加上 `_log_usage()` **之後**才跑的,每次 API 呼叫的 token 數都即時記錄在 `llm_usage_log.jsonl`——本篇第 7 節的 token 數字是**真實記錄,不是離線估計值** |

---

## 3. 核心發現一:無安全網下的 Trial 浪費率

**跳過率** = 該模式所有 run 中,被記成「重複 config,已跳過」的 trial 比例。跳過率越高,
代表這個記憶策略越常「忘記」自己已經試過某個配置,在固定 30-trial 預算下,實際能拿來
產生新資訊的 trial 就越少。

| 模式 | 總 Trial 數 | 跳過數 | 跳過率 | 有效 Trial 數 |
|---|---|---|---|---|
| **Full**(全部歷史) | 90 | 27 | **30.0%** | 63 |
| Tool(工具檢索) | 90 | 36 | 40.0% | 54 |
| Window(滑動視窗) | 90 | 40 | 44.4% | 50 |
| Summary(LLM 摘要) | 90 | 44 | **48.9%** | 46 |

**Fisher's exact test(跳過率兩兩比較)**:Full vs Summary p=0.014(顯著),Full vs Window
p=0.064(邊緣顯著),其餘組合不顯著。**Full 模式的記憶可靠度顯著優於 Summary**——這跟先前
用「隱藏重試次數」間接估計出的排序一致,這裡是用真實浪費掉的 trial 直接驗證,不再是估計值。

---

## 4. 核心發現二:安全網只換效率,不換決策品質

把同一模式在「有安全網」(`final_results_30`)與「無安全網」(`final_results_30_noretry`)
兩種條件下的**有效 trial** 分數分布拿來比較:

**Mann-Whitney U 檢定**:full p=0.72、summary p=0.86、window p=0.26、tool p=0.56,**全部不顯著**。

這代表安全網**只影響「浪費掉多少 trial 名額」**,不影響「LLM 一旦給出新建議時,這個建議的
品質」——這兩件事是獨立的。安全網把原本會發生的重複建議「攔下來重打」,讓表面上的浪費率
看起來很低,但代價是每個模式背地裡多燒的 API 呼叫次數(在有安全網的版本裡,這體現為
Full 平均只需要 7.7 次隱藏重試,Summary 卻要 47.7 次——關掉安全網後直接看到的跳過率排序,
跟這個隱藏重試次數的排序完全吻合)。

---

## 5. 核心發現三:即使浪費,LLM 有效 Trial 仍全面優於統計方法

把 4 種 LLM 模式(no-retry,只計有效 trial)跟 `final_results_30` 的 TPE / NSGA-II /
Random(同樣 30 trial,有安全網)做 trial-level 池化比較:

| 方法群 | Trial 數 | 平均分 | 中位數 | 正向率 | 災難率 |
|---|---|---|---|---|---|
| LLM(no-retry,有效 trial) | 213 | −0.19 | 4.00 | **60.1%** | **8.5%** |
| 統計方法(final_results_30) | 270 | −5.60 | −1.94 | 44.1% | 33.0% |

Mann-Whitney U 檢定:**p < 0.000001**,高度顯著。

即使 LLM 模式因為記憶不足而浪費掉 30%~49% 的 trial 名額,**剩下真正產出新資訊的 trial**,
品質仍然遠勝統計方法。換句話說:**LLM 的核心優勢(迴避災難性配置的先驗知識)跟記憶設計的
可靠度是兩個獨立的維度**。就算把記憶做得再差(沒有安全網、沒有 retry),LLM 每一次真正
做出的決策,依然明顯優於隨機或黑盒的統計搜尋。記憶設計的差異,影響的是「效率」(浪費多少
trial 名額才能達到同樣的探索深度),不是「安全性」。

## 6. Best Score 對照(run-level,3 run 平均)

| 方法 | Best Score 平均 | Std |
|---|---|---|
| LLM-Full(no-retry) | **4.698** | 0.026 |
| Random(final_results_30) | 4.645 | 0.034 |
| LLM-Window(no-retry) | 4.643 | 0.118 |
| LLM-Tool(no-retry) | 4.612 | 0.092 |
| LLM-Summary(no-retry) | 4.598 | 0.120 |
| TPE(final_results_30) | 4.603 | 0.005 |
| NSGA-II(final_results_30) | 4.578 | 0.023 |

Run-level 最終最佳分數在「no-retry 的 LLM」跟「有安全網的統計方法」之間沒有顯著差異
(Mann-Whitney U=77,p=0.11)——這跟前面所有比較一致:**最終分數這個指標本來就已經飽和**,
不管換哪一種記憶設計、有沒有安全網,搜尋空間本身的天花板都差不多,差異只會顯現在
「過程」(trial 浪費率、決策品質分布),不會顯現在「終點」。

## 7. Token 成本分析(真實記錄,非估計)

### 7.1 原始平均用量(每 run,3 run 平均)

| 模式 | 平均呼叫數 | 平均 Input Tok | 平均 Output Tok | 平均總 Tok | 相對 Full 倍數 |
|---|---|---|---|---|---|
| Window | 30.0 | 65,507 | 5,544 | **71,051** | 0.64x |
| Summary | 35.0 | 70,215 | 6,859 | 77,074 | 0.70x |
| Full | 30.0 | 104,921 | 5,346 | 110,268 | 1.00x |
| Tool | 53.0 | 151,506 | 8,688 | **160,194** | 1.45x |

**Tool 模式的成本明顯最高**(平均每個 run 要燒 53 次 API 呼叫、16 萬 token,是 Full 的
1.45 倍)——這是多輪工具檢索設計的直接代價,每個 iteration 平均要額外呼叫 ~1.8 次工具
檢索,再加上最終輸出決策的呼叫。**Window 帳面上是四者中最省的**(30 次呼叫、7.1 萬 token)。

值得注意的是:在**無安全網**設計下,重複建議不會產生「隱藏重試」的額外 token 成本
(因為 `_MAX_DUP_RETRIES=1` 根本不會重打 API,直接記成浪費 trial),所以這裡的 token 數
純粹反映「決策 + 工具呼叫 + 摘要更新」本身的成本,不含任何重試開銷。

### 7.2 性價比:把浪費率也算進 token 成本(本文新增分析)

7.1 的平均用量是「每個 run 花掉多少 token」,但沒有考慮到 §3 的跳過率——**同樣是 30 次
呼叫,Full 有 21 次真正產出有效 trial,Window 卻只有 16.7 次**(30 trial × (1 − 跳過率)/ 3
run)。把總 token 除以「有效 trial 數」,得到每個真正有效產出所付出的真實成本:

| 模式 | 平均總 Tok(每 run) | 有效 Trial 數(每 run) | **每有效 Trial Token 成本** | 相對 Window 倍數 |
|---|---|---|---|---|
| Window | 71,051 | 16.7 | 4,263 | 1.00x |
| Summary | 77,074 | 15.3 | 5,026 | 1.18x |
| Full | 110,268 | 21.0 | 5,252 | 1.23x |
| **Tool** | 160,194 | 18.0 | **8,900** | **2.09x** |

調整浪費率之後,排名整個翻轉:

- **Window 帳面最省,調整後依然最省**——雖然跳過率是四者中第二高(44.4%),但它每次呼叫
  本來就便宜(不帶完整歷史),浪費掉的那些 trial「機會成本」也相對便宜,所以性價比反而
  是最好的。
- **Full 帳面不是最省,但調整後只比 Window 貴 23%**——它跳過率最低(30.0%),浪費最少,
  幾乎每一次呼叫都有換到產出,抵銷了它「每次呼叫都比較貴」的先天劣勢。
- **Summary 帳面第二省,調整後跟 Full 幾乎打平**——它靠犧牲跳過率(48.9%,四者最高)換
  到便宜的帳面數字,但真正拿到手的有效 trial 很少,兩相抵銷後性價比並沒有比 Full 好。
- **Tool 無論哪個口徑都是最差的**——帳面最貴(1.45x)、有效 trial 也不是最多(18 次),
  調整後每個有效 trial 要花掉近 9,000 token,是 Window 的兩倍多,是四者中唯一「多花錢
  也沒換到對應品質或效率」的模式(§6 顯示它的 Best Score 也是四者最低)。

**結論**:單看 §7.1 的帳面 token 數會誤判 Window 和 Summary 的真實成本效益;把 §3 的跳過率
一併考慮進去後,**Full 和 Window 是性價比最好的兩個選擇,Tool 是唯一在任何口徑下都不划算的模式**。

## 8. 結論與建議

**核心結論**

1. **拿掉安全網後,記憶設計的優劣一次看清**:Full 模式跳過率最低(30.0%),Summary 最高
   (48.9%),兩者差異達統計顯著(Fisher's exact test p=0.014)。
2. **安全網只換掉「浪費多少 trial」,換不掉「決策品質」**:同一模式在有/無安全網下,有效
   trial 的分數分布沒有顯著差異(4 個模式 p 值都 > 0.25)。
3. **LLM 的核心優勢不靠安全網撐著**:即使拿掉安全網、浪費掉 3~5 成 trial 名額,剩下的
   有效 trial 品質仍全面輾壓統計方法(正向率 60% vs 44%,災難率 8.5% vs 33%,p < 0.000001)。
4. **最終分數這個指標已經飽和**:不管記憶設計、有無安全網,run-level 最佳分數全部打平
   (p ≥ 0.11),下一步不該再拿這個指標當主要比較依據。
5. **把 token 成本按浪費率調整後,Full 與 Window 性價比最好,Tool 最差**(§7.2)——多輪
   工具檢索的額外成本,沒有換到更高的分數或更低的浪費率。

**下一步該加哪些實驗**

- **把 `final_results` / `final_results_30`(5-retry 版本)也補上真實 token 記錄**:
  `_log_usage()` 只在這批 no-retry 資料開始跑之後才生效,5-retry 的兩組舊資料目前仍只能
  靠離線重建 prompt 去估計 token 成本(見 [`final_results_analysis.md`](final_results_analysis.md))。
  若要精確比較「有安全網」跟「無安全網」的真實 token 成本差異(而不是本文 §7 這種只能
  單獨看 no-retry 的真實數字),需要重新跑一次 5-retry 版本才能拿到對等的真實記錄。
- **guiding LLM 消融**:四種記憶策略目前都固定用同一顆 gpt-4o 做決策,換一顆較弱的模型
  (如 gpt-4o-mini)能檢驗「LLM 的核心優勢」是否隨模型能力遞減。
- **換模型 / 換任務**:目前所有結論都只驗證過 Llama-3.2-3B-Instruct + GSM8K,是最大的
  效度威脅,優先度高於再多跑幾次同一組設定。
- **長 trial 數驗證**:no-retry 消融只跑了 30 trial,若想驗證「summary/window 的記憶缺陷
  會不會隨 trial 數增加而更嚴重」,值得挑 1-2 個模式跑 50-80 trial,觀察跳過率的成長曲線
  是否持續惡化。
